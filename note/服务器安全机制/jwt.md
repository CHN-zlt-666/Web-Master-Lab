- jwt：一种类似于session的服务器安全机制，更完整的存放用户的信息。
- 与session的不同之处：
  1. session存放的是编号，浏览器发送编号给服务器之后，服务器根据编号匹配用户。而jwt是存放了用户的完整信息加上签名，浏览器发送到服务器之后，服务器只需要判签名是否正确即可。
  2. jwt不能被修改，当修改后，对应的签名会发生改变，导致jwt内容失效。
  3. seesion存在一种缺陷情况：如果说服务器没有把session存放到数据库里，当服务器进行重启后，session会失效。

# jwt的组成：

1. header：用于存放算法签名名称，以及告知为jwt的内容。
2. payload：存放信息。
3. signature：签名。即：在将前二者进行base-64url编码后，进行算法加密再次编码得到的内容，这也是jwt安全的关键，攻击者修改了header以及payload之后，由于不知道secret，无法计算出正确的signature，因此服务器可以发现jwt被篡改

# jwt的一些其他问题：

1. jwt的保存问题：浏览器不会自动保存jwt，需要php代码将jwt当作cookie保存到浏览器
2. jwt的生成问题：在login_jwt文件中可见每次在输入账号密码后，jwt都会生成。这是因为jwt以cookie的形式存放在浏览器中，涉及到cookie的生命周期
3. header，payload的拼接以及编码问题：在文件中可见，二者的拼接与编码均是进行了两次
   - 第一次拼接是为了生成签名，第二次拼接是将三者结合到一起形成jwt
   - 第一次编码是正常编码操作，第二次编码是对二者的拼接得到的内容进行加密后的编码
4. 为什么使用base64url编码：为了保证jwt能够安全的存放在url，cookie等传输位置，不会因为特殊字符出现解析问题

# 弱密钥爆破：

- 原理：将可能的密钥进行存放，一一测试通过这些密钥生成的签名是否和正确的签名相同
- 这也引出了最核心的一点：密钥。密钥是生成签名的关键，安全的关键是保证密钥的不泄露

# 靶场实操：

1. jwt核心思想简单，主要难点在于生成jwt过程中对php函数的利用
2. 在jwt_tool文件中做了简单的弱密钥爆破工具，再利用jwt_create文件根据baopo出的密钥得到jwt
3. 得到jwt后，怎么进入admin后台：
   - 因为登录框的限制，当从数据库查询出user身份后，直接跳转到user界面，无法访问admin界面。只需要修改cookie中存放的jwt，然后直接访问admin页面即可。这是因为jwt是从浏览器发送到服务器进行解析。（因此，若管理员jwt泄露，也存在一定风险）
4. 对于alg=none的漏洞，更多是业务逻辑漏洞

# 防御：

1. 不外泄密钥，使用强密钥，使攻击者拿不到密钥，无法修改jwt
2. 固定算法（针对于alg=none问题）
3. 设置生命周期，但该点只能减少jwt泄露后被长期使用的风险。
