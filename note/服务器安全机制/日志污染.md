# 服务器日志

- 日志的作用：服务器记录访问信息的东西，分为access log访问日志，error log错误日志
- 日志的内容是根据客户端进行发送的数据，日志并不会进行判断，而是直接记录，所以说引出了后续的日志污染问题

1. 日志真正记录的内容：
   ```php
    客户端IP
    访问时间
    请求方法（GET/POST）
    URL
    HTTP版本
    状态码（200、404、500）
    返回大小
    Referer
    User-Agent
    Cookie（有些配置会记录）
    Host
   ```
2. 可能污染的地方：**User-Agent**，Referer，URL，COOKIE

- 在这一部分，相较于之前的内容更多涉及于php的内容，但是从现在开始，更多是围绕php + web服务器 + 操作系统三者共同进行 (在lfi.php文件中可详细见，php代码很少，更多是围绕web服务器进行的攻击以及防御)

3. 日志污染开始，决定成败的是web服务器，不同的服务器存在不同的日志位置，日志格式，记录内容

# 日志污染

- 日志污染在一定程度上与文件上传漏洞相似：二者均需要在上传或者污染成功后，找到一个执行口去执行，否则前面做的铺垫无效：、
  1.  文件上传漏洞：在通过图片马进行绕过限制后，在该项目里面若不存在一个include接口去访问，图片马所包含的php代码则无法执行
  2.  日志污染：通过污染日志，存放php代码后，不能被include，则攻击连断裂
  - 二者均不是有日志就成功或者上传就成功的简单攻击，而是背后有一整条不可分裂的攻击连

## 防御方式

- 基于现代服务器来讲，防御方式更多是去断开这个完整的攻击连，所以引出一下防御方式：
  1.  通过白名单限制include，也就是用户无法控制参数，在根本上阻断了日志污染的最后一步
  2.  加上文件权限
  3.  禁用危险函数
  - 错误的防御方式：将日志文件进行隐藏，改名。攻击者可以通过大量信息收集进行得到文件地址以及名称

- 基于以上结论，引出深度思考：**现代服务器的防御方式，并不是针对于去防御某一个漏洞，真正的攻击不是利用了某个漏洞，而是将众多细小漏洞连接起来形成一个完整的攻击链，所以说在防御操作里，在攻击链里面的每个环节都需要进行障碍设置**

# 靶场实验：

- include一些补充内容：通过url进行了目录穿越后，读取到了log日志文件，如果想进行动态后门的搭建，那函数的作用起点是log文件还是lfi文件呢？因为log文件只是数据来源，而执行代码的页面还是lfi，所以说需要对lfi文件进行相对路径的操作

  (在上述实验过程发现了一个问题：日志里面user-agent的内容被双引号进行包裹，也就是php代码相当于只能用到单引号，后续的复杂代码需要用到单双引号交替使用，但这种情况会导致出现日志加上/去区分双引号，后续的复杂代码无法执行，暂未想出解决方案)
  - 具体日志引号问题代码

  ```php
  127.0.0.1 - - [30/Jun/2026:14:40:49 +0800] "GET /vuln/upload/file_upload.php HTTP/1.1" 200 241 "http://web-master/users/user.php" "<?php echo\"test\"; ?>"
  ```

- 日志污染内容：最开始在遇到上述情况时，发现先注入的错误php代码(也就是上述引号问题)会导致后续php代码不执行，就想到了可以在日志里面故意存放一个错误语法的php代码，导致后续攻击者的php代码无法执行的防御方式

  (但资料查明却说，如果攻击者可以控制注入日志的顺序，吧攻击代码放在错误语法前，这种防御方式就没用了，但还未验证)
