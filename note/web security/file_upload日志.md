# 基础知识：

1. 本质上来说，文件都只是一些字节流，并非我们眼中的php文件是代码，jpg文件是图片
2. 文件头：文件头的作用是程序判断文件类型的关键，因为后缀名可以被随意更改，比如我将一个jpg文件后缀改为php后缀，但文件不会变成php代码，所以文件真正是什么不由后缀决定，所以就存在了第一种漏洞：开发者检测文件后缀进行放行，后续引出了getimagesize函数，图片马
3. web服务器决定执行什么，jpg文件，直接返回内容，html返回网页，php交给php解析器，所以说不是php来执行文件，而是web服务器
4. 文件名与路径，进行穿越目录使用：

   完整文件路径：路径+文件名，所以说存在某些风险攻击者可以上传类似于../../shell.php文件名，当拼接之后可以控制上传路径，意味着可以控制文件存放位置，产生漏洞

5. php上传机制以及众多函数

# 文件上传漏洞原理以流程：

- 服务器把用户上传的可访问文件当作程序执行
- 流程：
  1. 用户上传文件，php进行接收之后保存到服务器
  2. 用户访问该文件
  3. 服务器根据文件类型进行执行操作 (如果这里是恶意代码程序文件，那么就产生漏洞)
- 上传成功+可访问+可执行才能满足文件上传漏洞，缺一不可

# 为什么文件上传看似限制简单，但还是存在这种漏洞：

1. 只检查文件名，攻击者可以通过修改文件名：shell.php.jpg进行绕过上传检查，但实际上并不会产生漏洞，因为文件最终还是jpg类型 (但在某些历史漏洞中，还是会造成攻击，见后续笔记)
2. 检查来自content-type内容为image，但是可以通过bp抓包修改，但不影响实际文件类型
3. 服务器的一些特殊解析规则
4. 历史兼容：限制php，但存在php3,php4等文件后缀
5. 图片马

- 本质来说：开发者进行开发时过度信任用户发送的文件请求内容，而攻击者就是利用这一点进行绕过防御规则实现的文件上传漏洞
- 核心思想：上传漏洞不是利用文件类型进行的攻击，更多的是开发者的判断与服务器判断不一致 (1,3中提到的内容)、

# 图片马的一些基础知识补充：

1. jpeg结构：不是简单的文件头+图片数据组成，而是由数据块+图片数据组成，里面可以存放拍摄时间等一些备注，所以说jpeg天然允许存放额外数据
2. png结构：由众多数据块组成，所以说png也是允许存放额外数据

- 基于以上两种类型，存在metatata元数据，里面存放了额外信息，所以说元数据是安全方面所需要特别关注的

# **项目靶场测试**：

- 在白名单防御操作里面，通过bp抓包进行对文件后缀的修改进行绕过了白名单，但是在访问文件的时候发现服务器把文件当作图片处理了，那为什么说文件后缀名修改不会直接把文件从代码变成图片，这句话本身是没问题的，问题出在：用户访问文件的时候，服务器根据后缀进行解析，所以如果要产生漏洞，需要服务器存在一个特殊规则去处理文件
- 图片马的一些操作问题：
  1. 图片马进行了绕过文件头的操作，但是后缀依旧是jpg，文件即使上传成功，但是内容却没有执行，所以说文件上传漏洞的三个条件缺一不可
  2. 执行的缺口：手动搭建lfi接口进行了图片马的执行 (若服务器存在特殊解析规则，图片马依旧可以进行执行。也可以进行上传.htaccess文件进行覆盖操作)
  3. 在二次渲染图片里面进行了初级图片马的基本防御
  4. 对于目录穿越，php自动进行了对../的限制，靶场里面并没有得到验证，但资料提到过在某种特殊环境下，该漏洞风险仍存在
  5. 后续研究路径：
     - EXIF COMMENT图片马，更难检测
     - PNG IDAT绕过二次渲染
     - 利用 imagecreatefromjpeg() 的容错

**总结**

- 文件上传漏洞的本质：攻击者成功控制了服务器上的可访问文件，并且让服务器将该文件交给php解释器进行处理，从而实现代码的执行
- 防御核心思想：围绕着 “限制php代码的上传” 和 “限制文件被php解释器进行处理” 的核心思想
